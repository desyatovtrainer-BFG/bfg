 1. What this project does

  BFG — Big Fitness Game is a gamified fitness web app for Russian-speaking users. It is   

  explicitly not a fitness tracker. The design philosophy frames it as an "emotional       

  self-evolution system": users complete workouts, earn XP, level up, evolve a personal    

  avatar, and receive support from a calm AI companion. The product is built around        

  retention through emotional attachment, not performance metrics. The target geography is 

  Russia (Kinescope for video, Russian payment systems in the roadmap, companion phrases in   Russian, offline-first companion logic to avoid VPN dependency).

  5. Architectural risks

  a. awardXp partial failure. In lib/progression/award-xp.ts:89–105, if the XP write       

  succeeds but the avatar update fails, XP is granted but avatar evolution is silently     

  skipped. The comment says "на следующем awardXp догоним" — but there's no retry trigger. 

  The avatar can get stuck at a lower visual stage until the next XP event.

  b. Five empty placeholder directories. modules/, types/, hooks/, constants/, shared/ all 

  exist and contain zero files. Types live inside individual lib/*/types.ts files. This is 

  minor but signals organizational drift — the planned structure was never adopted.        

  c. Next.js 16 is genuinely different. [AGENTS.md](http://AGENTS.md) warns about it explicitly. The project   

  uses proxy.ts instead of middleware.ts (a Next.js 16 change). Any future code changes    

  must be validated against node_modules/next/dist/docs/ — training data from Next.js      

  13/14/15 patterns will silently fail.

  d. Subscription system is a skeleton. requirePremium() redirects to /profile (hardcoded  

  path, no dedicated subscription screen). No payment provider is connected. The comment in   access.ts acknowledges this: "Сейчас фич за пейволлом нет — это фундамент." This is MVP 

  debt but blocks monetization.

  e. ensureBfgProfile on every authenticated page load. app/(app)/layout.tsx:31 calls this 

  on every navigation inside the app shell. It's idempotent, but it's still an

  unconditional DB roundtrip. As traffic grows this will be noticeable.

  f. No workout content tooling. Content is managed manually via Supabase Table Editor     

  (documented in WORKOUT_CONTENT_[GUIDE.md](http://GUIDE.md)). This is a deliberate MVP decision but creates a   bottleneck for content scale and is fragile (no validation, no bulk tools).

  g. LLM companion path is unclear. The companion is intentionally local/deterministic     

  because OpenAI doesn't work reliably from Russia without a VPN. When LLM calls are       

  eventually added, the geo-political constraint will need a solution (proxy, alternative  

  provider, or server-side relay via Vercel edge).

  6. Most important parts of the app

  Ranked by centrality to the retention loop and current code maturity:

  1. lib/progression/ — The most complete and best-documented system. XP, level

  calculation, streak logic, and avatar evolution thresholds all live here with clean      

  separation. Everything else (quests, workouts, companion) feeds into it.

  2. lib/companion/build-companion-message.ts — The emotional core. Deterministic,

  geo-safe, and notably well-engineered for MVP: FNV-1a hash produces a stable daily phrase   without randomness or external calls. Drives user perception of being "seen."

  3. app/(app)/layout.tsx — The auth guard and profile bootstrap for every authenticated   

  screen. If this breaks, the entire app breaks. ensureBfgProfile here also handles        

  first-login state creation.

  4. Workout completion loop (lib/workouts/actions.ts → awardXp → avatar update) — The     

  primary XP source. This is the main action the product is designed around; it triggers   

  progression, companion feedback, and avatar evolution.

  5. lib/quests/ — Daily engagement driver. Controls streak maintenance and daily return   

  behavior — directly tied to the retention metric the product is built around.
